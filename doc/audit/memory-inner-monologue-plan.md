## 0. 结论摘要

1. **病根判定：是「该写时不写」（触发问题），不是「写了但记不准」（质量问题）。**
   证据：线上 135+ 个群聊会话里 `memory_append` 调用 **0 次**；模型自己的推理里也从未出现过「印象/记住/值得记」
   （群聊 0 个会话，私聊 6 个）。但群聊记忆里现在有 5 位成员 22 条印象 —— 全部由**代码跑的批量整理管线**
   在 10-20 09:01 补齐，不是模型在会话里记的。
2. **机制现状：线上当前的人设走 override 分支，系统提示里根本没有记忆段。**
   `memoryRules()`（含「偶尔用，别当笔记本」）只在默认分支拼装；线上 `persona.systemPromptOverride` 非空，
   走 `src/prompt.js:251-265`，只保留安全规则/工具协议/技能/附加规则。整份系统提示 3209 字符里
   与记忆有关的只有工具协议第 1 条的一句「所有需要长期记住的东西写进记忆工具」。
3. **thinking 现状：应用不发思考参数，模型默认思考；thinking 内容已拿到但无人消费。**
   线上 `thinkingMode=auto`、`thinkingEffort` 为空 → `resolveThinkingRequest()` 得 `on=false`，
   `buildThinkingParams()` 不发送任何思考字段；但网关仍返回 `reasoning_content`（333/394 次调用，
   中位 298 字符，最大 6127 字符）。`llm.js:512-516` 把它提取成 `result.reasoning` 后**没有任何消费方**；
   原始响应作为 `session.messages[].raw` 整份落盘，UI 不展示，只有会话详情「JSON 模式」能看到。
4. **成本量级：加一段 100 字左右的提示词，每天约 2 万 token、约 0.003 元，可忽略。**
   按实测 1.012 字符/token、每会话 2.12 次调用、当天 87 次运行、89.2% 前缀缓存命中估算
   （基数为当天 2,162,446 prompt token）。
5. **推荐：方案 A（加一段「先判断再决定」）+ 方案 D（整理管线降阈值做机制兜底）+ 记忆条目 provenance 记账。**
   方案 A 是「内心戏」本身且最贴合用户原话；方案 D 是唯一不依赖模型自觉的机制；provenance 是验收能算数
   的前提（现在记忆条目只有 `content/createdAt`，无法区分「模型记的」与「整理生成的」）。
   **没有证据支持「写了但记不准」**（没有读原文做质量标注，见 §2.3）。
6. **新方向「人物画像」的答复见 §8：该做，但做窄 v1。** 画像 = 记忆的渲染形态（不建新库、不做关系图）：
   每条印象加 2–3 个可选字段（`dim`/`origin`/可选 `sessionId`）+ 渲染时按人合成画像段（≤3 人×120 字）+ 内心戏口令走 reasoning
   （不要求正文输出）+ override 分支修复 + provenance。整理口径与阈值改动在 `orchestrator.js`（task-5 写域），留到 v1.1。
   画像段 ≤420 字符/调用、≤900 token/会话，额外成本 ≤¥0.01/天。

## 1. 现状（代码 + 线上）

### 1.1 `src/thinking.js` 现在做什么

四件事，全部是「参数/文本的形状处理」，不碰业务：

| 职责 | 位置 | 说明 |
|---|---|---|
| 方言检测 | `detectDialect()` `:92-111` | 域名优先 + 模型名兜底；分 deepseek/qwen/glm/openai-o/anthropic/gemini/openrouter/xai/ollama/local-openai/generic |
| 构造请求参数 | `resolveThinkingRequest()` `:139-162`、`buildThinkingParams()` `:172-251` | 按档位 off/low/…/max 和方言决定发 `thinking`/`enable_thinking`/`reasoning_effort`/`reasoning`/`extra_body` |
| 提取思考文本 | `extractReasoning()` `:283-312` | 兼容 `reasoning_content`/`reasoning`/`thinking`/`thoughts`/`reasoning_details`/content 数组 |
| 提取思考 token | `extractReasoningTokens()` `:315-322` | 从 usage 各处取 `reasoning_tokens` |

线上实测：`api.model=deepseek-flash`、`api.baseUrl` 是第三方网关（非 deepseek.com）、`thinkingMode=auto`、
`thinkingEffort` 空。`resolveThinkingRequest()` 里 `effort=''`、mode 不是 on/off → `on=false`；
`buildThinkingParams()` 对 deepseek 方言只在明确 on/off 时加参数 → **请求体里没有任何思考字段**。
但 394 次调用里 333 次响应带 `reasoning_content` —— 思考是模型/网关的默认行为，不是应用开关开出来的。
换个默认不思考的模型，这条通道会静默消失；反过来把 `thinkingEffort` 设成 off 也挡不住当前模型的默认思考。

### 1.2 thinking 内容从 API 拿到后是保留还是丢弃

- **拿到**：`src/llm.js:511-516` 每次响应都 `extractReasoning(result.message)`，有内容就写 `result.reasoning`。
- **产物无人消费**：全仓 grep `.reasoning` 只有 `llm.js:515` 的赋值和 `thinking.js` 内部；`orchestrator.js`
  只用 `response.extraUsage.reasoningTokens` 记账（`orchestrator.js:1269-1275`）。
- **原始数据仍在盘上**：`orchestrator.js:1286-1293` 把 `response.raw` 整个塞进 assistant 条目，
  `sessions.js` 又把整个会话 JSON 落盘 → 每次调用的 `reasoning_content` 都在
  `data/sessions/<id>.json → messages[].raw.choices[0].message.reasoning_content`。
- **不进下一次运行**：`prompt.js` 的模型是「零历史」，每次只发系统提示 + 用户提示；上一轮的 assistant 文本
  （包括 reasoning）不会被带回去。
- **UI 只展示正文，不展示 reasoning**：会话详情里 assistant 条目的卡片是「💭 思考 / 不发送」，
  内容取 `item.content`（`ui/app/02-sse-sessions.js:626-640`）；`reasoning_content` 只在「JSON 模式」
  （`:550-576`）里以原样 JSON 出现。

结论：**「会话有没有可用的中间推理文本」——线上每次调用几乎都有（333/394），已经落进会话记录（在 `raw` 里），
但系统没有任何代码在用它，UI 也没有把它当成「内心戏」展示。**

三个工具（`src/tools.js:648-723`），都只在 `memberImpression` 分类下工作：

触发指引有两处，**都偏弱且线上只剩一处**：

1. `src/prompt.js:125-132` `memoryRules()`：【轻量记忆：偶尔用，别当笔记本】三行 —— 有「记什么」的边界，

2. 工具协议第 1 条（`src/prompt.js:38`，override 分支也会拼）：
   「你没有跨次运行的对话记忆，所有需要长期记住的东西写进记忆工具。」—— 陈述能力，不是触发动作。

### 1.4 记忆写入的另一个主体：自动整理管线

`orchestrator.js:1059` 每次运行收尾都调 `#maybeConsolidateMemory()`（`:1922-1951`），条件与行为：

| 项 | 值 | 位置 |
|---|---|---|
| 触发门槛 | 全群印象总数 > 4，或任一成员 > 5 条 | `:1942-1945`、`:1751-1753` |
| 冷却 | 默认 6 小时（`memory.consolidateMinIntervalMs`） | `:1754`、`config.js:344` |
| 整理对象 | 已有印象的成员；外加「发言 ≥ 20 条且零印象」的活跃成员（每次最多 3 人） | `:1837-1853` |
| 整理方式 | 已有：只减不增（条数变多视为幻觉放弃）；新建：从最近 40 条发言提炼 | `:2003-2041`、`:2063-2086` |
| 输出 | 整体替换该成员印象（≤5 条，每条 ≤120 字），并把全部 `createdAt` 重置为当前时刻 | `memory.js:524-569` |

这解释了线上记忆的现状：群聊 5 位成员 22 条印象、私聊 1 位 4 条，**全部 `createdAt` 集中在两次整理时刻**

**记忆条目没有 `origin` 字段**，事后无法区分「模型自己记的」和「整理生成的」（见 §6）。

## 3. 病根判定

1. **主因是触发，不是质量。** 模型能记（私聊 8 次证明它会调工具），但群聊里没有触发它的东西：
   线上系统提示的记忆段被人设 override 整段挤掉，剩下的只有工具描述里「只记…不要太临时」的边界，
   以及工具协议里一句陈述句。模型没有「每轮该扫一眼要不要记」的动作。
2. **第二个主因是「谁在维护记忆」这个事实没有被设计对齐。** 线上真正在写记忆的是整理管线（每 6 小时、
   面向发言 ≥20 条的成员），模型自身几乎不参与维护（`memory_query` 0 次、`memory_remove` 1 次）。
   用户说的「内心戏有助于记忆维护」，要落在「会话内即时写入/更新」这一段，**不能替代**整理管线：
   管线管「补」和「压缩」，内心戏管「及时」。
3. **辅助原因（设计缺口，会让验收算不出来）**：记忆条目没有来源标记，整理会把 `createdAt` 全量重置，
   导致「模型记的」与「整理生成的」事后不可区分。任何方案落地前先补 provenance，否则 §5 的验收无法归因。

## 4. 方案对比

> 成本口径（可复核）：
> - 每次调用 prompt token 实测均值 = 4,589,685 / 393 ≈ **11,679 token**（含系统提示、用户提示、工具 schema）；
> - 每会话调用数 = 393 / 185 ≈ **2.12**；当天运行数 **87**；当天 prompt token **2,162,446**；
> - 字符→token 换算取「单次调用会话」实测：306,956 字符 → 303,263 token ≈ **1.012 字符/token**；
> - 价格（price-feed 缓存，deepseek-flash 闲时）：in 1、out 4、cached 0.02 元/百万 token；
>   线上缓存命中 89.2%，增量 token 按 0.892×0.02 + 0.108×1 ≈ **0.125 元/百万 token** 折算。
> - 公式：Δtoken/天 = 段落字符数 × 1.012 × 2.12 × 87 ≈ 字符数 × 187。

| # | 方案 | 怎么做 | token 增量（实测基数估算） | 与现有 thinking / 发送路径的冲突 | 实现成本 | 可判定性 |
|---|---|---|---|---|---|---|
| **A** | 系统提示加一段「先在心里判断再决定」 | 在 `src/prompt.js` 的**always-rendered 区**（override 分支也拼）加 109 字符，例：「每轮看完消息，先在心里过一遍：有人的话里带了关于他自己的、以后还用得上的稳定信息吗？有就在本轮结束前用 memory_append 记一条；只是这轮的话题就跳过，不用说出来。」 | +109×1.012×2.12 ≈ **+229 token/会话**；**约 +2.0 万 token/天**（当天基数 0.95%）；**约 ¥0.0026/天** | 落在提示词里，交给模型自己的通道：模型可以在 reasoning 里判断（当前模型默认思考，几乎总有的通道），也可以写正文。**与 PASS 协议有冲突**：AI 判定不接时必须「只输出标记」，文案必须写「不用说出来」，否则 PASS 轮会多出文字。与 `prompt.js:43`「内心不要写伪代码」不冲突 | 最小（改一段文案 + 修 override 分支） | 可直接 A/B |
| **B** | 收尾隐藏 `memory-candidate` 块，代码解析入库 | 系统提示加 99 字符，要求「有稳定信息就输出一行 `<memory userId=…>一句话</memory>`，没有不输出」；orchestrator 在 rescue/发送之前解析、入库、把块从正文剥掉 | 指令 +99×1.012×2.12 ≈ **+208 token/会话**（约 1.8 万/天）；命中时多 40–80 个 **输出** token（out 价 4 元/M；一天几十次命中 ≈ ¥0.01/天级） | 收益是「不占工具轮次、可审计候选块」；但正文输出会**变多**，与 PASS 协议冲突（PASS 轮不得输出块，需要在判定不接时跳过）；与回复安全网（`src/reply-rescue.js`，当前线上未装 reply-safety 插件，`/opt/aichat/app/plugins` 只有 smart-wake/token-saver）理论上冲突——将来装了插件，块文本可能被当草稿「抢救」进群 → 必须在 rescue 之前剥块并加断言 | 中高：解析器、去重、剥块、provenance、防泄漏断言、测试 | 最好：块可落档审计 |
| **C** | 只改工具描述 + 一行触发条件 | 在 `memory_append` 描述里加 76 字符：「第一次透露关于自己的稳定信息时就该记一条，不用等到第二次；每次会话最多 1~2 条」 | +76×1.012×2.12 ≈ **+160 token/会话**（约 1.4 万/天，0.67%）；≈ ¥0.0018/天 | 不新增输出通道，无发送风险；但仍是「提示词约定」，按机制优先级是四者里最弱的一档（见 §7 引用） | 最小 | 可 A/B |
| **D** | 不加提示词，改机制：整理管线降阈值 + 事件触发 | `discoverMinMessages` 20→5、`discoverMaxMembers` 3→5；并把「同一冷却窗口内每次运行后异步整理」改成「发现新活跃成员即整理该 1 人」；provenance 必做 | **prompt 增量 0**；额外整理调用：新建模式每次 1 调用（prompt 约 1–8k token，取决于该成员最近 40 条发言长度；out 约 60–120 token），按 8–24 次/天估算 **¥0.01–0.19/天**。若把冷却从 6h 降到 1h，调用量 ×6（20–140 次/天，¥0.03–1.2/天） | **无 thinking 冲突**（不碰提示词与发送路径）。代价是限流与成本上限要一起定；且它只在「整理时刻」生效，**解决不了会话内即时记忆** | 中（改配置默认 + 事件触发 + 限流 + provenance） | 延迟/覆盖率可测 |

**方案之间的关系：** A/C 是「让模型在会话里想起来记」，B 是「让模型把候选交给代码」，D 是「不指望模型，代码自己补」。
A/C/B 都是在提示词上做约定，D 是机制；A+D 不重复，B 与 D 可叠加。

**推荐：A + D + provenance。** 理由：
- A 是用户要的「内心戏」本身，token 代价可忽略，改动最小；
- 但按「约定 ≠ 机制」的判据（AI 不遵守时会发生什么：什么都不会发生，只是继续不记），A 单独不足以算解决；
- D 用现有已被证明在跑（线上 22+4 条印象就是它产的）的管线兜底，把「新成员在几小时内被补上」变成机制；
- provenance 是 A/D 共同的前置：没有它，§5 的写入率与误记率都算不出来。

### 5.3 负向对照（缺一即不算通过）

- **内容负向**：负向集误记率 ≤10%，且正负写入率差 ≥30pp —— 只测「正向变高」不测「负向不乱写」等于没排除「多写就是好」。
- **成本负向**：token 增量必须在理论区间内，且 cached 占比不能明显下降（防止把动态内容塞进系统提示破坏前缀缓存）。
- **安全负向**：故意构造「模型在无工具调用时输出隐藏块 / PASS 轮输出内心戏」的用例，断言不发送、不破坏 PASS。
- **质量负向**：必须抽检误记（一次性事件被记成长期印象），不能只看写入数量。

## 6. 实施前置：记忆条目 provenance

现状（`src/memory.js:203-220`）：条目只有 `{ content, createdAt }`；整理替换（`:524-569`）会把所有条目
`createdAt` 重置为整理时刻。后果：今天无法回答「这 22 条里哪些是模型自己记的」。

最小改法：条目加 `{ origin: 'model' | 'consolidate', sessionId?: string }`；`append()` 传 `origin:'model'` 与当前会话 id，
`replaceConsolidated()` 传 `'consolidate'`；读取侧兼容旧条目（缺省视为 `'consolidate'`）。
这条改动很小，但没有它，§5 的判据 1/2/3/8 全部算不出来。

## 7. 风险与不做的事

- 不做：改生产代码、commit、切分支、重启/停服务、跑全量 `npm test`（并行任务在改 `src/`）。
- 不做：读群友原文做人工标注 —— 所以「该记没记」的逐条真实发生率在本文标记为**未验证**，不写估计数字。
- 风险 1：A/C 都是提示词约定，可能「改了也没用」。用 §5 的 A/B 判据当场判，不通过就升到 B 或只保留 D。
- 风险 2：A 若让模型把判断写进正文，会撞 PASS 协议与未来的 reply-safety 抢救路径；文案与断言里已覆盖。
- 风险 3：思考通道不可依赖 —— 线上思考是模型默认行为，应用没发参数；换模型/换网关后可能没有 reasoning
  （届时「内心戏」只能落在正文，输出成本与 PASS 冲突都变大）。
- 风险 4：A 加在系统提示会一次性让现有前缀缓存失效；按当前量级（每群一份缓存）影响可忽略，但**不要**把随轮变化的内容放进系统提示。

## 8. 方向修订：从「事实条目清单」升级为「人物画像」

> 用户新方向：内心戏的核心是提升对话质量；说话的质量不在话本身，而在对人物的了解，人物画像可能相当重要。
> 本节把记忆的主形态从「事实条目」修订为「人物画像」，回答数据模型、提示词位置与 token 账、内心戏用法、并行边界、质量验收与成本。
> §4 的方案 A–D、§5 的写入触发验收仍然有效；本节是补充与修订。

### 8.0 该不该做、做到什么程度

**该做，但只做「窄 v1」：画像做成「记忆的渲染形态 + 极少量结构字段」，不新建画像库、不做关系图、本轮不改整理口径。**

1. 现状瓶颈不在画像本身，在「模型根本不参与写记忆 + 记忆段进不了生产提示词」（§2、§8.7）。先修复这两条，画像才有素材。
2. 线上只有 26 条印象、5 位群友有画像素材（§2.1），画像质量在本轮无法被证明；按可验收的最小改动推进。
3. 仓库里画像的唯一消费方是提示词（`formatForPrompt()` 只被 `prompt.js:867/908` 调用，测试在 `coverage-offline.mjs:406`）——
   独立画像存储会是单消费者的浅层结构（删除测试不通过）。

用户原话里有两个不同对象，要分开存：

| 对象 | 归属 | 说明 |
|---|---|---|
| 人物画像 | 用户提示【记忆】段（随在场的人变化） | 每会话动态渲染 |
| 模型自己的「价值观」 | 系统提示/人设（`systemPromptOverride` 或 `roleText`），跨会话稳定 | 不是记忆工具，不该按天变；本轮不做「自动凝练价值观」（会改人设，属另一个机制；要做也输出人设建议 + 管理员确认） |

### 8.1 人物画像的数据模型（现有结构 + 最小新增）

**现有结构（`src/memory.js`，已核对）**

| 层 | 内容 |
|---|---|

| 成员文件字段 | `{ userId, name, impressions: [{content, createdAt}], updatedAt, lastConsolidatedAt }`（`:60-70`，写入 `:203-220`） |

**最小新增：每条印象加 2–3 个可选字段；不改文件布局、不改聚合方式**

| 字段 | 位置 | 用途 | 谁写 |
|---|---|---|---|
| `dim` | 每条 impression | 画像维度：`personality` 性格 / `tone` 语气 / `values` 在意什么 / `redline` 雷点 / `relation` 关系 / `fact` 事实（缺省） | 模型 `memory_append` 时可选传入；整理保留见下方 v1.1 边界 |

不新增的结构与理由：

- **不新增画像文件/画像库**：唯一消费方是提示词渲染，单消费者结构是浅层（删除测试不通过）。
- **不新增关系图**：关系用 `dim=relation` 的文本条目（「和某人是情侣」「对我像对小孩」）；结构化关系图没有第二个消费方。
- **不落 `lastSeenAt`**：渲染时从 `store.recent()` 现算，避免双写漂移；时间戳不进提示词正文（见 8.2 缓存约束）。

**哪些靠整理管线合成、哪些必须模型写**

| 画像要素 | 谁能产生 | 说明 |
|---|---|---|
| 性格 / 语气 / 在意什么 / 雷点 | **整理管线可合成**：`#buildConsolidatePrompt` 已在合并去重、只减不增；`#buildNewImpressionPrompt` 已在从最近 40 条发言提炼稳定特征 | 把「输出口径」从事实条目改成人物特征即可，但**要改 `orchestrator.js` 两段整理提示词（task-5 写域）→ 本轮不做，放 v1.1** |
| 关系（两人之间、与我之间） | **必须模型写** | 整理只读单个成员发言，看不到两人互动；「和我的关系」只有会话内的模型看得到 |
| 新特征首次出现 | **必须模型写**（`memory_append` 是唯一入口） | 正是 §2 的 0/135 缺口 |
| 更新/删除过时项 | 整理管线已覆盖 | 不是本轮重点 |

**整理会丢 `dim` 的边界**：`replaceConsolidated()` 只取 `content`（`:524-569`），整理后 `dim` 丢。
- **v1.0（本轮推荐，不碰 orchestrator）**：`dim` 只由 `memory_append` 写入；渲染时「有条目 `dim` 按 `dim` 排序，没有按 `createdAt` 降级」；接受整理后画像退化为纯文本。
- **v1.1（task-5 合并后）**：整理提示词输出 `{"impressions":[{"dim":"…","content":"…"}]}`，`replaceConsolidated()` 接受对象并保留 `dim`/`origin`。

### 8.2 画像怎么进提示词 + token 账

**位置：用户提示【记忆】段（`src/prompt.js:852-870`），不进系统提示。**

- 画像随「本次在场的谁」变化，属易变内容；系统提示是跨会话稳定前缀（`prompt.js:236-239` 明确要求动态段殿后，别打断前缀缓存）。
- 现有锚点机制把【记忆】+【已读信息】当跨轮稳定前缀（`prompt.js:773-804`）：同一锚点窗口内画像字节不变 → 命中缓存；锚点失效（新群友/窗口滚出）时已有整体重置兜底（`:700-703`）。
- **画像段内不许放时间戳/「最近互动于…」**：它每次变会把锚点判成 reset；`lastSeenAt` 只用于「选谁」不用于「写什么」。

**选取规则（复用现有 `relevantUserIds`，只加排序与截断）**：① 被 @/被引用的人 > ② 触发批最后发言的人 > ③ 已读窗口最近互动的人；取前 3 人（典型 2 人）。
锚定轮按 `anchorDecision.anchor.memberIds` 顺序取前 3（保证字节稳定）；窗口里新出现的成员仍走【新加入成员】段（`prompt.js:902-911`，已有逻辑）。

**渲染形态（不落库，渲染时合成；维度顺序固定）**

```
【记忆】你认识的群友（画像）
- 甲：<性格/语气>；在意 <…>；雷点 <…>；关系 <…>；<一条事实>
- 乙：…
```

每类取最新 1 条，没有就跳过；总字符受硬上限约束。

**硬上限建议**：最多 **3 人**、每人 **≤120 字**、画像段 **≤420 字符（≈415 token）/次调用**、**≤900 token/会话**；超限按 `fact → values → 第三人` 顺序截断。
依据：现状注入段中位 218 字符、实测最大 653 字符；`formatForPrompt()` 目前**没有字符上限**（成员多时理论上界 9 人×3 条×120 字 ≈3,500 字符 ≈3,470 token/调用），画像改造顺便把它变成有界。

**token 账**（1.012 字符/token；当天实测每会话 24,856 prompt token、2.12 次调用、87 次运行、2,162,446 token；有效价 0.1258 元/百万 token）

| 场景 | 字符 | token/调用 | token/会话 | 占每会话 | token/天 | 占当天 | 元/天 |
|---|---|---|---|---|---|---|---|
| 现状典型（实测中位） | 218 | 215 | 457 | 1.8% | 3.97 万 | 1.84% | ¥0.0050 |
| 现状实测最大 | 653 | 645 | 1,368 | 5.5% | 11.9 万 | 5.50% | ¥0.0150 |
| **画像 v1 典型（2 人）** | ~230 | 227 | 482 | 1.9% | 4.19 万 | 1.94% | ¥0.0053 |
| **画像 v1 上限（3 人）** | ≤420 | ≤415 | ≤880 | ≤3.5% | ≤7.65 万 | ≤3.54% | ≤¥0.0096 |

画像段相对现状中位的增量是 **+25 token/会话**，按上限也只有 **+380 token/会话（+1.6%）**；钱可忽略（≤¥0.01/天）。真正的成本是实现与误记风险，不是 token。

### 8.3 内心戏的正确用法

**v1：内心戏走模型自己的 reasoning 通道，不要求正文输出。** 依据（均已实测/查码）：

1. `result.reasoning` 无消费方（`llm.js:512-516` 赋值后没人读）；`reasoning_content` 已随 `messages[].raw` 落盘（333/394 次调用）→ 放 reasoning 里**零代码可观测、可离线验收**。
2. `[[PASS]]` 协议只认正文（`#aiJudgeRoundVerdict({rawContent})` 调用段，`orchestrator.js`，且先于 rescue）；正文加短块会污染这条协议。
3. reply-safety 只对**正文**生效（`src/reply-rescue.js` 头注释：「判错了就是把内心戏发进群」）；线上未装该插件（`/opt/aichat/app/plugins` 只有 smart-wake/token-saver），但将来装了，正文短块有被当草稿抢救进群的风险。
4. 输出 token 按 out 价（4 元/M）计，约是缓存输入价的 200 倍；正文内心戏每轮都付，reasoning 本来就在生成。
5. 当前模型默认思考，通道稳定；**换成不默认思考的模型**时会静默失效 → 那时才降级到「正文前可丢弃短块」（§4 方案 B，需解析/剥块/防泄漏断言）。

**v1 口令（并入记忆段文案，不新增可选步骤）**：开口前先在心里确认「这句话像不像对这个人说的：他吃不吃这套、会不会踩雷、我们熟不熟」；判断不出声、不影响 PASS。
**分工**：画像由代码确定性渲染（模型不用回忆），内心戏只负责「用不用、怎么用」。

**验收内心戏是否生效（不改代码）**：从 `session.messages[].raw...reasoning_content` 抽改动前后的 reasoning，统计「开口轮次里出现目标群友名字/人物判断词（性格/语气/雷点/熟）」的比例；PASS 轮断言 `content` 严格等于标记（负向）。

### 8.5 验收判据（对话质量代理指标 + 负向对照）

**主实验（离线、固定夹具、可重复）**

- 固定 **20 条「需要按人物调整语气」的输入**，每条标注 1 位目标群友 + 期望语气方向（如「对雷点多的人少开玩笑」「对熟人可吐槽」）。
- 三臂对照（同一模型、temperature 0.8、每条 3 次）：
  - (a) **无画像**（现状：事实清单格式）
  - (b) **画像正确**（v1 渲染）
  - (c) **画像错配**（把 A 的画像换给 B）——强负向对照
- 判定：第二个模型按固定 rubric 盲评 + 人工抽检 20%；要求 **画像 > 事实清单 > 无画像 > 错配**；
  「画像」比「无画像」通过率 **≥ +20pp**；**错配臂不得高于无画像臂**（若错配也变好，说明模型没真用画像 → 判失败）。
  这组同时就是「没有画像时同一批输入应当更差」的对照：无画像/错配变差才证明画像在起作用。

**机械断言（免费、进回归）**

- 画像段出现在用户提示【记忆】位置；人员正确（对得上 trigger/@ 的人）；≤3 人、每人 ≤120 字、段 ≤420 字符。
- 锚点稳定：同一会话连续两轮、成员不变时，画像段字节完全一致（防时间戳等易变内容混入）。
- token：每会话增量在理论值 [0.5,1.5]×；cached 命中率下降 ≤5pp。
- `origin` 记账：模型写入为 `model`、整理写入为 `consolidate`。

**内心戏断言**：改动后开口轮次的 reasoning 里出现目标人物指向词的比例显著高于基线；PASS 轮 `content` 严格等于标记（负向）。

**线上 7 天**

- `origin='model'` 条目 ≥1/天；单成员 ≤5 条、单条 ≤120 字；整理管线无新增失败（`[memory]` 日志分类计数）。
- 质量只能人工抽检：每天抽 10 条含【记忆】注入的会话，按 rubric 判「有针对性 / 模板复读 / 踩人物雷点」；「踩雷」必须为 0（负向红线）。
- 编造红线：问「你记得我什么」类输入，答案必须来自画像；编造率 ≤5%（人工抽检 20 条）。

### 8.7 单独问题：override 非空导致 memoryRules 不进提示词——什么性质、要不要修代码

**判定：产品设计缺陷（机制段与人格段被同一种「整段替换」处理）+ 三处口径不一致；不是现场配置错误，也不是崩溃型 bug。**

证据链：

1. 现场配置合法：管理员用 `deploy/apply-persona.sh` 把人设卡注入 `persona.systemPromptOverride`（热更新，不重启）；配置面只有 `tools.memory` 工具开关（当前开着），没有「记忆提示段」开关，用户没有要求去掉记忆。
2. 仓库内两条已确立的口径都站在「机制不该被 override 吃掉」一边：
   - `test/persona-dedup-test.mjs` 头注释：「工具协议/分条/表情/唤醒/**记忆**等机制只由 `src/prompt.js` 承担，两层都不再重复」；
   - `deploy/apply-persona.sh` 注释：「`systemPromptOverride` 会整体替换**人格/风格准则**，只强制保留 securityRules() 与 toolProtocol()」。
3. 代码行为却是：override 分支把 `memoryRules()`/`stickerRules()`/`qqSceneRules()`/`reportBan()` 一并丢弃（`src/prompt.js:251-265`）；
   `doc/extend_development/prompt-pipeline.md:55` 又写成「2~9 段人格/行为规则整体被用户写的文本替换」——三处口径互相矛盾。
4. 线上实测影响：生产系统提示 3209 字符，无【轻量记忆】、无表情包/QQ 场景/汇报禁令段；记忆只剩工具描述与工具协议一句。

**修它要动代码：要（最小改动只在 `src/prompt.js`）。** 纯配置绕过（把记忆段抄进 override 文本）可行但不推荐：第二事实源、人设一改就丢、无测试守卫，且与 dedup 测试的分工冲突。

**最小修法（规格，不写实现）**

1. 在 `prompt.js` 标注「机制段」清单（本轮只归入 `memoryRules()`；sticker/qqScene/reportBan 是否同归由产品一次拍板，别只修一半）。
2. override 分支在「安全规则 + 工具协议」之后追加机制段（顺序：override → 安全 → 工具协议 → 记忆 → 技能 → 附加规则），与默认分支语义一致。
3. 同步 `doc/extend_development/prompt-pipeline.md` 的覆盖模式描述（「人格/风格段可被替换；机制段强制保留」），否则下一个人会把缺陷当设计。

**判据（可判定）**

- 单测：`buildSystemPrompt({persona:{systemPromptOverride:'自定义人设'}})` 输出含【轻量记忆】，且【安全规则】【工作方式】仍在；默认分支同一套断言（两分支等价）。
- 抽查：部署后任意新会话 `session.systemPrompt` 含该段；字符增量 = 201 ±10%（`memoryRules()` 实测 201 字符）。
- 回归：`node test/ai-judge-test.mjs`（PASS 协议不受影响；发送路径未动）；prompt 缓存命中率下降 ≤5pp（一次性失效可接受）。
- 改动落在 `src/prompt.js`，与 task-5 / task-8 / task-11 写域不相交（§8.4）。
